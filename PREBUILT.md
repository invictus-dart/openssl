# OpenSSL prebuilt bundles

Fork of [openssl/openssl](https://github.com/openssl/openssl) used only to build and publish
static OpenSSL libraries for the target triples the `mars` Dart package needs.

The mars hook links OpenSSL statically into a single plugin dynamic library. Building OpenSSL
from source inside the hook does not work everywhere — most notably on Windows hosts, where
`perl Configure` emits a POSIX Makefile and requires `rm`, `chmod` and `make`. Publishing
per-triple bundles once removes that local toolchain dependency entirely.

## Asset contract

| property | value |
| --- | --- |
| file name | `openssl-<version>-<suffix>.tar.gz` |
| root directory | exactly the file name without `.tar.gz` |
| contents | `include/openssl/*.h`, `lib/libcrypto.{a,lib}`, `lib/libssl.{a,lib}`, `build-info.json`, `LICENSE.txt` |
| excluded | `applink.c` (Windows-only helper, never useful for static consumers) |

The root directory name matters: the mars hook extracts with plain `tar -xzf` and infers the
source directory from the asset name, so a mismatch breaks the download path.

Public headers are shipped per bundle because 28 of them are generated by `Configure`. Only
`configuration.h` is architecture specific (`SIXTY_FOUR_BIT_LONG` vs `THIRTY_TWO_BIT`, `bn_ll`,
`rc4_int`, per-target `OPENSSL_SYS_*`), but `crypto.h`, `md5.h`, `rand.h` and the rest must
still come from the same version and configure invocation as the archives. All static headers
are byte identical across bundles; `verify-matrix.sh` enforces this.

## Suffixes and configure targets

| suffix | configure target | runner | notes |
| --- | --- | --- | --- |
| `linux-x86_64` | `linux-x86_64` | ubuntu-24.04 | native |
| `linux-ia32` | `linux-x86` | ubuntu-24.04 | needs `gcc-multilib` |
| `linux-aarch64` | `linux-aarch64` | ubuntu-24.04 | `--cross-compile-prefix=aarch64-linux-gnu-` |
| `linux-armv4` | `linux-armv4` | ubuntu-24.04 | `--cross-compile-prefix=arm-linux-gnueabihf-` |
| `android-arm64` | `android-arm64` | ubuntu-24.04 | NDK r28c, `-D__ANDROID_API__=24` |
| `android-arm` | `android-arm` | ubuntu-24.04 | same |
| `android-x86_64` | `android-x86_64` | ubuntu-24.04 | same |
| `android-x86` | `android-x86` | ubuntu-24.04 | same |
| `macos-arm64` | `darwin64-arm64` | macos-14 | `-mmacos-version-min=11.0` |
| `macos-x86_64` | `darwin64-x86_64` | macos-14 | `-mmacos-version-min=10.15` |
| `ios-arm64` | `ios64-xcrun` | macos-14 | `-mios-version-min=12.0` |
| `ios-simulator-arm64` | `iossimulator-arm64-xcrun` | macos-14 | `-mios-simulator-version-min=14.0` (clang clamps this slice to 14.0) |
| `ios-simulator-x86_64` | `iossimulator-x86_64-xcrun` | macos-14 | same |
| `windows-x64` | `VC-WIN64A` | windows-2022 | MSVC x64, NASM x64 |
| `windows-arm64` | `VC-WIN64-ARM` | windows-11-arm | MSVC arm64 toolset; this target has no `asm_arch`, so Configure disables asm and NASM is not needed |
| `windows-ia32` | `VC-WIN32` | windows-2022 | MSVC x86, NASM x86 |

The `windows-arm64` leg cannot run on `windows-2022`: that image carries no ARM64 MSVC toolset,
so `vcvarsall arm64` leaves `cl`/`jom` unset. `windows-11-arm` is the ARM64 image upstream's
`os-zoo` uses for the same target.

Apple bundles ship the oldest deployment target each slice supports (`macos-arm64` cannot go
below 11.0). A prebuilt archive cannot follow every consuming app's deployment target, and any
newer app target links against a lower floor without complaint.

Android is cross-compiled on a Linux runner on purpose: the NDK ships native linux-x86_64 host
binaries, so no Rosetta or x86 macOS runner is involved. Apple targets still need macOS because
only Xcode carries the SDKs.

## Checks performed per bundle

1. `configuration.h` and `crypto.h` exist and are the generated variants.
2. `libcrypto`, `libssl` archives exist.
3. `libcrypto` defines `MD5` and `RAND_bytes` — the only OpenSSL entry points mars links
   against (`OPENSSL_thread_stop` is referenced by the Windows thread shim only).
4. `smoke.c` compiles and links against the bundle (native triples also run it, which proves
   the RFC 1321 `MD5("abc")` digest and a working `RAND_bytes`).
5. The archive extracts to a root directory equal to the asset name.

`scripts/verify-matrix.sh` then cross-checks the whole matrix: naming, archive contents, pointer
width reported by `configuration.h`, and byte equality of every header other than
`configuration.h`.

## Repository switches

The workflow needs three repository settings that cannot be committed:

1. **Actions enabled.** A fork that inherits a large workflow set from upstream gets its Actions
   switched off by GitHub (*"Workflows are not currently being run on this fork due to the scale
   of GitHub Actions usage"*); a maintainer re-enables them from the Actions tab. This branch is
   an orphan carrying only `prebuilt.yml`, so a push here schedules exactly one workflow — the
   inheritance problem cannot come back while this branch stays the one being pushed.
2. **Settings → Actions → General → Workflow permissions** set to *Read and write*, so
   `gh release create/upload` can attach assets with `GITHUB_TOKEN`.
3. **Default branch = `prebuilt`**, or use the `push` trigger instead of the Run-workflow
   button: GitHub only lists a `workflow_dispatch` workflow in the UI when the file exists on
   the default branch. `master` is left as an untouched mirror of upstream, so switching the
   default branch to `prebuilt` is the cleaner of the two options.

## Running it

`workflow_dispatch` takes `tag` (OpenSSL tag to build) and `release` (release to publish under).
Re-running with the same release replaces assets in place (`gh release upload --clobber`), so a
rebuild does not invalidate previously published versions. Keep a `-r2` style release tag when
the archives change but the OpenSSL version does not, because consumers pin URLs and hashes.

Pushing to the `prebuilt` branch also triggers the build; `master` is kept as a mirror of
upstream and carries no workflow.

## Local build

```sh
SRC_DIR=/path/to/openssl-3.5.9 OUT_DIR=$PWD/out ./scripts/build-unix.sh 3.5.9 linux-x86_64 linux-x86_64
```

```powershell
.\scripts\build-windows.ps1 -Version 3.5.9 -Target VC-WIN64A -Suffix windows-x64 -VcArch x64 -SrcDir .\src
```

Both scripts run the same sequence as the mars hook:

1. `perl Configure <target> no-shared no-pinshared no-apps no-tests no-docs` plus the platform
   flags the hook derives from the consumer's code config — `-D__ANDROID_API__=24` on Android,
   the `-m*-version-min` floors above on Apple — then `--prefix=<stage> --libdir=lib`.
2. `build_libs` with a parallel build: GNU `make -j<n>` on unix, `jom /J <n>` on Windows (the
   hook builds with jom because nmake has no parallel mode), with `CL=... /FS` on Windows so
   parallel `cl` invocations stop colliding on `ossl_static.pdb` (C1041).
3. `install`, which is what the hook runs; `install_sw` on Windows with `/J 1` so the `depend`
   rules cannot race over `makefile` (Error 13). Docs are excluded by `no-docs`.
4. Only then the Windows-only `applink.c`, `bin/`, `lib/cmake` and `lib/pkgconfig` are dropped —
   nothing the FFI consumer reads.
